# i18n & accessibility

## Internationalization

### Setup

Android resources. Every module owns its strings in `src/main/res/values/strings.xml` (the default
table — the source language, every key) with translations in `values-<locale>/strings.xml` next to it:

```
feature/gallery/impl/src/main/res/
├── values/strings.xml         ← default table — every key lives here
├── values-fr/strings.xml      ← add when localizing (a translation may omit keys: they fall back to values/)
└── values-es/strings.xml
```

- **Every Android library module prefixes its keys with its `resourcePrefix`** (`gallery_…`, `core_ui_…`; set in
  the module's build file, enforced by Lint). All modules' resources merge into one table in the APK — two
  modules' `title` keys would silently override each other. `:app` is exempt (its `app_name` and start-placeholder
  strings stay unprefixed); the form-factor apps (`:wear`, `:tv`, `:automotive`) prefix theirs anyway.
- **Per-app language**: `androidResources { generateLocaleConfig = true }` (the app convention) plus
  `app/src/main/res/resources.properties` (`unqualifiedResLocale=en-US`) publish the app's languages to
  the system's per-app language settings (Android 13+) — nothing else to add. An in-app picker on Android 13+
  calls the framework's `LocaleManager.setApplicationLocales(...)`. Below 13 (minSdk 29 reaches Android 10)
  only AppCompat can apply a per-app locale: `AppCompatDelegate.setApplicationLocales(...)` there works only in
  `AppCompatActivity` hosts (with an AppCompat theme, and `autoStoreLocales` to persist the choice). `MainActivity`
  is a `ComponentActivity`, so an in-app picker for those versions means switching it to `AppCompatActivity` —
  record that as an ADR.
- **Pseudolocales** (`en-XA` long text, `ar-XB` RTL) — enable `isPseudoLocalesEnabled = true` on the debug
  build type when checking layouts for truncation and mirroring.

### Usage

```kotlin
@Composable
internal fun GalleryEmptyState(modifier: Modifier = Modifier) {
    Text(stringResource(R.string.gallery_empty), modifier = modifier)
}
```

**Anti-pattern**: hard-coded user-facing strings. Every `Text(...)` argument and every `contentDescription`
reads from resources.

Errors: `:core:domain` carries a sealed `DomainError`; `:core:ui`'s `DomainError.toMessage()` words the
built-in cases from `:core:ui`'s table; a screen words the typed errors (`DomainError.Typed`) it reacts to
from its own table. A ViewModel holds **which** message (`@StringRes pendingMessage: Int?`), never resolved
text; the screen resolves it inside the effect that consumes the slot, through resources captured outside it
(`val resources = LocalResources.current`, then `resources.getString(id)` in the `LaunchedEffect` — a
`CompositionLocal` can't be read inside an effect).

### Pluralization

```xml
<plurals name="gallery_photo_count">
    <item quantity="one">%d photo</item>
    <item quantity="other">%d photos</item>
</plurals>
```

```kotlin
Text(pluralStringResource(R.plurals.gallery_photo_count, count, count))
```

### Number / date formatting

`java.time.format.DateTimeFormatter.ofLocalizedDate(FormatStyle.MEDIUM)` and `NumberFormat.getInstance(locale)`
(or `android.icu.text.*`) — locale-aware by construction. Never format dates with a hand-written pattern for
display.

## RTL (right-to-left)

Every scaffolded project is **RTL-ready** by default.

### Convention

Never use `Modifier.padding(left = ..., right = ...)`. Always:

```kotlin
Modifier.padding(start = 16.dp, end = 16.dp)
```

`start`/`end` flip automatically when the locale is RTL (Arabic, Hebrew, Farsi). `left`/`right` are absolute and break RTL layouts.

Same rule for:
- `Alignment.Start` / `Alignment.End` (not `Alignment.Left` / `Alignment.Right`)
- `Modifier.absoluteOffset()` (avoid; use plain `offset` which is direction-aware)
- `TextDirection.Content` (the default, picks based on text content)

### Testing RTL

```kotlin
@Test
@Config(qualifiers = "ar")   // Robolectric: an RTL locale — or wrap in LocalLayoutDirection provides Rtl
fun galleryMirrorsInRtl() {
    composeRule.setContent { AppTheme { GalleryContent(…) } }
    composeRule.onRoot().captureRoboImage()   // an RTL golden next to the LTR ones
}
```

An RTL Roborazzi golden makes a mirroring regression visible in review.

The `android-reviewer` agent flags any new `left =` / `right =` modifiers.

## Accessibility

### Rules enforced

1. **`contentDescription` mandatory on `Icon` and `Image`**. Decorative icons use `contentDescription = null` (explicit, not omitted).

   ```kotlin
   // OK — meaningful icon
   Icon(Icons.Default.Search, contentDescription = stringResource(R.string.gallery_search))
   // OK — decorative
   Icon(Icons.Default.ChevronRight, contentDescription = null)
   // ANTI-PATTERN — flagged by reviewer
   Icon(Icons.Default.Search, contentDescription = "search")  // hardcoded string
   ```

2. **Minimum touch target 48dp** (Material guideline). Use the design token:

   ```kotlin
   object AppDimens {
       val touchTargetMin = 48.dp
   }
   ```

   Custom clickable Composables must size at least `AppDimens.touchTargetMin`:

   ```kotlin
   Modifier.minimumInteractiveComponentSize()      // Compose Material built-in
   // OR
   Modifier.sizeIn(minWidth = AppDimens.touchTargetMin, minHeight = AppDimens.touchTargetMin)
   ```

3. **No hardcoded `.sp` font sizes**. Always read from `MaterialTheme.typography`:

   ```kotlin
   Text(text, style = MaterialTheme.typography.bodyLarge)        // OK
   Text(text, fontSize = 16.sp)                                  // ANTI-PATTERN
   ```

   Reason: dynamic type scaling depends on theme-relative sizing. Hardcoded sp ignores user font-size preferences.

### Other a11y conventions

- **`testTag`** on every interactive element that needs to be reachable in tests. Use a stable convention: `<screen>:<element>` (`gallery:retry`; a list item adds its ID: `gallery:photo:<id>`).
- **`Modifier.semantics { }`** for grouping (e.g. `mergeDescendants = true` on rows that should announce as one item).
- **Focus order** — default is reading order; override only when layout breaks expected traversal.
- **High contrast** — design tokens must clear WCAG AA contrast against background. Validate via Material Theme Builder or manual check.

### Enforcement

Android Lint's accessibility checks (`ContentDescription`, `ClickableViewAccessibility`, `RtlHardcoded`,
`HardcodedText`) read XML layouts and Views — in Compose code they see nothing. For Compose:

1. **Slack's compose-lints** (in `lint`, warnings are errors) and **compose-rules** (ktlint, `spotlessCheck`) —
   Compose API usage a11y builds on: a `modifier` parameter on every UI composable (so callers can add semantics
   and sizes), Material 3 components (with their touch-target and semantics defaults), hoisted state.
2. **`android-reviewer` agent** — the accessibility rules themselves: a missing or hard-coded `contentDescription`,
   `.sp` literals, `left`/`right` padding, missing `testTag`, color literals outside `:core:designsystem`, touch
   targets below `AppDimens.touchTargetMin`.
3. **Tests** — screen tests find elements by text, content description and `testTag`, so an unlabeled control has
   nothing to find; `android-qa` journeys read `content-desc` from `android layout`, so unlabeled controls surface
   on a device too. The **Accessibility Scanner** app and TalkBack cover anything visual.

## Dark mode

Default-on. `AppTheme(themeMode, dynamicColor)` (`:core:designsystem`) resolves the scheme from the user's
stored `ThemeMode` — `MainActivityViewModel` observes it through `ObserveThemeModeUseCase` (DataStore-backed)
and `MainActivity` passes it in:

```kotlin
setContent {
    val state by viewModel.collectAsState()
    if (!state.loading) { // nothing renders until the stored theme is read: no wrong-theme flash on a cold start
        AppTheme(themeMode = state.themeMode) { AppNavigation(entryProviderInstallers) }
    }
}
```

`ThemeMode.SYSTEM` follows `isSystemInDarkTheme()`. `MainActivity` also re-applies `enableEdgeToEdge(...)` with the
resolved theme, so the system-bar icons follow the app's theme rather than the system's night mode. A settings screen offers Light / Dark / System and calls
`SetThemeModeUseCase`. Both brand schemes live in `AppColors.kt` (generate with
[Material Theme Builder](https://material-foundation.github.io/material-theme-builder/));
`dynamicColor = true` uses the wallpaper palette on Android 12+ instead.
